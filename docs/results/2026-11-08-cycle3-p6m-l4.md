# P6M student — 2026-11-08 cycle-3 run (Colab L4)

## What shipped

Code (`feat/chess-cycle3-scaling`, 14 commits):

- **>100M-position mixed corpus.** `build_cache --mix source:count` converts Lichess evaluation and GigaFish depth-10 shards in a process pool, splitting each parquet shard across its row groups so one 57M-row file no longer runs on a single worker. The build measured **119,613,619 records** (100,000,000 GigaFish + 19,613,619 Lichess) in 35 minutes, with per-source and depth-band counts, checksummed incremental manifests, and a format stamp that rejects a cache built with a different record layout.
- **Side-to-move canonicalisation.** Planes and policy/PV indices mirror to the mover; a colour-mirror test proves equal outputs for a position and its reflection, and the search maps its chosen index back to absolute coordinates.
- **Square-aware attention.** Learnable per-square positional embedding plus a smolgen generator that consumes per-square vectors instead of a pooled mean (attention-bias rank went from 1 to 27–30).
- **Continuous value + decoupled PV.** Records carry the centipawn score; value supervision regresses `2·P(win|cp) − 1` with the WDL head as an auxiliary classifier; PV has its own projections at weight 0.05 instead of sharing the policy projection at 0.5. The search consumes the trained value head.
- **Throughput work.** Batched shard reads (7.5M records/s gather), a prefetch thread, seeded shuffle, a probe slice the trainer never samples, 15-minute checkpoint cadence, and `torch.compile` — measured **3,094 pos/s** training on L4 (cycle-2 baseline 1,928 pos/s at a quarter of the batch size; forward-only throughput is 3,547 pos/s).
- **Sampler correctness.** Batches are drawn shard-major (a corpus larger than page cache makes a globally random gather read every shard per batch) but only two batches per shard before advancing, so a short run still sees every source.

## Diagnosis

**The engine is coherent but planless, and it is far too undertrained to beat a 1320 rung.** The diagnostic match is the informative one: against an engine that plays the first legal move, our engine drew all ten games and never lost material — but the games end in repetition (knight shuffling against rook shuffling). It does not blunder; it has no plan, so a 1320 opponent simply outplays it on every attack.

Three measured facts explain the ceiling:

1. **Training volume.** The evaluated checkpoint saw ~4M positions. The corpus holds 119.6M; one pass would need 117,000 steps at batch 1024, roughly 10 hours at the measured 3.1k positions/s.
2. **Policy signal density.** 84% of the corpus (GigaFish) carries no move target. The first run drew its batches shard-major and consumed only four shards, so its policy head trained on almost nothing — the interleaved rerun shows a live policy loss of 2.80 once fixed.
3. **Search compounding.** At ~30 simulations per move with a 6M network, search cannot compensate for a policy that proposes aimless moves.

## Deviations

- The ladder runs a fixed 100 ms/move rather than the plan's 1+0 clock: it makes rungs comparable, and the engine never approached its time budget anyway.
- ChessBench (`Lichess/chessbench-v1-lichess`, `google-deepmind/chessbench`) returns HTTP 401, so the corpus is two sources rather than three.
- The match sample is 10–20 games per rung, so the intervals are wide; the 0/0/20 result is decisive only in direction.
